# Security boundaries

MOONPAW is an offline single-player game with public source. A player who owns the device can alter source, files, memory or local saves. Client validation, disabling developer tools and ASAR packaging cannot make it cheat-proof. There is no competitive leaderboard, purchase entitlement or remote account to protect, and the app installs no DRM or kernel anti-cheat. If verified competitive scores are added later, a trusted service must validate gameplay/results; a secret embedded in the game would not establish that trust.

Progress is treated as untrusted input. Loading and storing reconstructs a bounded schema: integer chapter counts, finite bounded result values, known chapter IDs and exact unique witness keys. Invalid and oversized saves fall back safely; extra fields, inherited properties and prototype keys are discarded. Existing legitimate chapter unlocks and records remain compatible. These controls prevent malformed saves breaking the interface and fake arbitrary witness strings unlocking the ten-witness choice; they do not prove that a valid-looking local record was earned.

The Windows renderer has no Node integration, runs with context isolation and a sandbox, and exposes only quit/fullscreen operations. Every IPC operation requires the current window's main frame, exact application origin and entry document. Production developer tools are disabled. A non-packaged official Electron development shell may explicitly enable `MOONPAW_TEST=1` for automated checks; the packaged app ignores that test switch. The preload exposes only a frozen context-bridge test boolean, not environment or Electron APIs.

The custom protocol serves read-only files inside `dist` from the exact `moonpaw://game` host. Malformed encodings, alternate separators, drive paths, Windows streams and unsupported file types are rejected. Responses have a content policy that restricts scripts and network connections to packaged same-origin resources, prohibits frames/plugins and disallows eval. Inline style is allowed for existing chapter artwork and HUD presentation; inline script is not. All permission requests/checks are denied, webviews and subframe navigation are blocked, and external links are restricted to the exact published creator and instrument-license destinations.

The controls are regression-tested against oversized/malformed saves, fake and duplicate witness keys, inherited/prototype keys, malformed and foreign protocol URLs, untrusted IPC frames and external-link substitutions. Native smoke checks are also needed after release builds to verify the actual Electron boundary and legitimate fullscreen/exit/audio behavior.

See the primary [Electron security guidance](https://www.electronjs.org/docs/latest/tutorial/security), [custom protocol API](https://www.electronjs.org/docs/latest/api/protocol) and [Electron fuses](https://www.electronjs.org/docs/latest/tutorial/fuses). ASAR integrity and executable signing are separate packaging controls. Integrity fuses require a correctly embedded archive hash; unsigned executables can still be replaced by a device owner. Release SHA-256 digests help users compare downloads but are not anti-cheat.
